# 数字

`ruststream-amqp` 的基准测试数字测的是什么，以及不能从中得出哪些结论。

## 与裸客户端的对照 {/* #the-comparison-against-a-raw-client */}

同一行中的三个循环可以互相比较，因为它们在同一个进程中、交替地、对着同一个 Broker 运行。一行不能与另一个 Broker crate 公布的行比较：各种传输在每条消息上做的工作不同。换一个 AMQP 1.0 Broker，一行中的三个数字会一起变动，所以 Broker 的镜像与数字一起公布。

Broker 运行在同一台机器上，走回环接口。没有网络延迟，同样的每条消息开销在时间中所占的比例，比面对跨网络的 Broker 时更大。应把该百分比读作已部署服务所付代价的上界。

差值为负来自提前读取，而不是代码省下的开销：本 crate 的订阅在上面的循环工作时继续接收，裸循环则不会。

`受 Broker 限制` 的行表示消费者在运行的大部分时间里都在等 Broker。本 crate 和运行时的工作于是发生在这段等待之内，测出的差异接近零。这是开销的下界，而不是对它的测量。

## 代码的开销 {/* #the-cost-of-the-code */}

指令计数包含本 crate 的代码、它上面的运行时，以及 `fe2o3-amqp` 客户端在服务线程上的工作。由于 Broker 是真实的，它在各次运行之间会有少许变动。同样的计数在缓存未命中处要花更多时间，因此计数不等于时间。

每个数字都是稳态，即 1000 次投递的运行与 2000 次投递的运行之差。建立连接、附加链路以及它们背后的首批内存分配属于冷启动，只付一次。

## 它们不意味着什么 {/* #what-they-do-not-mean */}

一行就是一个消费者读取一个 queue 地址，消息体很小，只有一个 Broker。它测量的是一次投递在本 crate 内部的开销，而不是 Broker 能承载多少。

对照只测量消费一侧。一次发布在服务线程上的开销，是代码图中的应答那一行。发布的吞吐量受 Broker 往返时间的限制，因为一次发布要等待它的 disposition，[路径](../path.md)一页用图说明了这一点。

这些数字是一台机器在某一天的快照，构建信息记录在旁边。它们在一台只做这次运行的机器上手动重新测量：它们显示的差异小于共享机器的噪声。
