# AMQP 1.0

`ruststream-amqp` - брокер AMQP 1.0, построенный на [`fe2o3-amqp`](https://docs.rs/fe2o3-amqp).
Протокол - стандарт ISO, поэтому один крейт обслуживает ActiveMQ Artemis, RabbitMQ 4.x, Azure
Service Bus, Amazon MQ, Solace, Apache Qpid и IBM MQ. Понятия самого фреймворка (написание
подписчиков, маршрутизация, кодеки, middleware) объясняет
[документация RustStream](https://powersemmi.github.io/ruststream/).

```toml
ruststream = { version = "0.7", features = ["macros", "json"] }
ruststream-amqp = "0.7"
serde = { version = "1", features = ["derive"] }
```

## Прелюдия {#the-prelude}

`use ruststream_amqp::prelude::*;` - единственный импорт, который пишет файл сервиса. В нём брокер
и его профиль `Sasl`, дескриптор адреса и его гарантия `Settle`, политики публикации, `AmqpError`,
трейты-совместимости, которыми обработчик ограничивает свои слоты, и прелюдия самого фреймворка.

Сервис пишется на двух словарях. Тело обработчика называет совместимости, поэтому там достаточно
одного `ruststream::prelude::*`: каждый слот ограничен той совместимостью, которая нужна телу
(`Out<impl Publisher>`, `Out<impl TransactionalPublisher>`, `Out<impl RequestReply>`), а конкретного
издателя даёт точка монтирования. Файл маршрутов называет политики: он импортирует этот glob, где
они лежат без брокерного префикса:

| Корень крейта | В прелюдии |
|---|---|
| `AmqpPublish` | `Publish` |
| `AmqpTransactionalPublish` (фича `transaction`) | `TransactionalPublish` |

Поэтому на любом брокере точка монтирования читается как `b.include(handler).out(Reply, Publish)`,
и перенос сервиса с брокера на брокер меняет один импорт, а не каждую точку монтирования. Имя
политики кончается на `Publish`, а имя трейта-совместимости её живой формы - на `Publisher`, поэтому
два словаря нигде не совпадают по именам. Исходные имена с префиксом тоже экспортированы - для
файла, который импортирует glob сразу двух брокерных прелюдий и должен сказать, о каком `Publish`
речь.

## Совместимости {#capabilities}

Необязательные трейты-совместимости фреймворка и то, что этот брокер реализует нативно:

| Совместимость | Нативно | Примечание |
| --- | --- | --- |
| `Subscribe` | да | подписка по имени; имя - это адрес, он передаётся дословно |
| `BatchSubscriber` | да, на клиенте | [одна передача доставляет одно сообщение, поэтому пакеты собирает буфер фреймворка](#batches) |
| `TransactionalPublisher` | да, с фичей `transaction` | [транзакционная отправка](#transactions), одна транзакция на стороне брокера на дескриптор |
| `OwnedTransactions` | нет | транзакция принадлежит дескриптору издателя, а не отдельному значению |
| `RequestReply` | да | [`reply-to`, `correlation-id` и динамическая связь для ответа](#requestreply) |
| `Partitioned` | да | [ключ партиционирования - это свойство `group-id`](#headers-and-the-partition-key) |
| `Seekable` и `Positioned` | нет | протокол не даёт позиции, на которую клиент мог бы перемотать |
| `DescribeServer` | да | сообщает хост и порт из URL соединения, без учётных данных, которые тот может содержать |
| Настройки публикации на сообщение | нет | [публикация не содержит секции `header`, поэтому месту вызова нечего настраивать](#publishing) |

## Жизненный цикл брокера {#the-lifecycle}

Брокер - это последовательность переходов, каждый из которых поглощает `self`, поэтому каждое
состояние оказывается отдельным типом:

```text
AmqpBroker::new(url)      только конфигурация, синхронно, без ввода-вывода
  .connect()   ->  ConnectedAmqpBroker      живое соединение; подписки и издатели
  .shutdown()  ->  ()                       завершает сеансы и закрывает соединение
```

`new` только записывает URL, поэтому сервис собирается синхронно, а рантайм подключается один раз на
старте. `shutdown` поглощает подключённый брокер, поэтому публикация или подписка после него не
компилируется. Издатель, выданный раньше, соединением не владеет, а разделяет его: после `shutdown`
он возвращает ошибку, а не выполняет успешную публикацию в закрытое соединение.

На синхронной форме вы можете задать аутентификацию и имя сервиса. `sasl` принимает профиль
`Sasl::anonymous()`, `Sasl::plain(user, pass)` или `Sasl::external()`, а `container_id` называет
сервис брокеру, по умолчанию `"ruststream"`. URL с учётными данными (`amqp://user:pass@host`) сам по
себе выбирает PLAIN, а явно заданный профиль важнее его. Для точки подключения `amqps://` нужна фича
`rustls` или `native-tls`.

Каждая подписка работает на собственном сеансе AMQP, а издатели делят между собой один общий сеанс.
Окна управления потоком считаются на сеанс, поэтому медленный потребитель не отнимает пропускную
способность ни у издателей, ни у другой подписки.

## Адресация {#addressing}

AMQP 1.0 стандартизует формат передачи, но не смысл адреса, поэтому намерение называет
`AmqpAddress`. Каждый конструктор объявляет соответствующую возможность терминуса - по ней Artemis и
другие продукты их различают:

| Конструктор | Семантика | Возможность терминуса |
| --- | --- | --- |
| `AmqpAddress::queue(name)` | anycast: конкурирующие потребители, каждому по одной доставке | `queue` |
| `AmqpAddress::topic(name)` | multicast: доставка всем подписчикам разом | `topic` |
| `AmqpAddress::raw(address)` | дословно, под собственное соглашение развёртывания | нет |

Дескриптор пишется прямо в атрибуте подписчика:

```rust
--8<-- "crates/ruststream-amqp/examples/amqp_service.rs:handler"
```

Сервис называет брокер один раз и монтирует на него обработчик:

```rust
--8<-- "crates/ruststream-amqp/examples/amqp_service.rs:app"
```

У дескриптора есть две настройки:

- `credit(nonzero!(n))` задаёт, сколько неурегулированных доставок брокер может держать у этой
  подписки одновременно. По умолчанию 256. Кредит - это собственное обратное давление протокола,
  поэтому меньшее значение ограничивает объём незавершённой работы. Подписка без кредита не получает
  ничего, поэтому счётчик - это `NonZeroU32`, а `credit(0)` не компилируется.
- `settle(Settle::AtMostOnce)` переводит подписку на доставку at-most-once: получатель урегулирует
  каждую доставку сразу при получении.

Дескриптор с пустым адресом отвергается до любого ввода-вывода.

Простая строковая форма `#[subscriber("orders")]` тоже работает: имя становится `AmqpAddress::raw`.

## Пакеты {#batches}

Обработчик, который принимает срез, получает пакет сообщений вместо одного, а размер пакета называет
точка монтирования:

```rust
--8<-- "crates/ruststream-amqp/examples/amqp_batches.rs:handler"
```

```rust
--8<-- "crates/ruststream-amqp/examples/amqp_batches.rs:app"
```

В AMQP 1.0 нет пакетного чтения: одна передача доставляет одно сообщение, а кредит управляет потоком
и не задаёт размер пакета. Поэтому пакеты собираются на клиенте: в пакете не больше сообщений, чем
названо в точке монтирования, и меньше, когда за это время больше не пришло.

`batch_wait` у дескриптора - это срок, по которому закрывается неполный пакет, по умолчанию 10
миллисекунд. Больший срок даёт более полные пакеты на редком трафике; на ровном потоке пакет раньше
закрывает размер, и срок не срабатывает. Кредит и размер пакета независимы: кредит ограничивает то,
что брокер держит у подписки, а размер - то, сколько сообщений видит один вызов обработчика.

## Подтверждение и диспозиции {#acknowledgement-and-dispositions}

Результат обработчика - это диспозиция протокола:

| Результат обработчика | Диспозиция | Что происходит |
| --- | --- | --- |
| `HandlerOutcome::ack()` | `accept` | доставка завершена, брокер её удаляет |
| `HandlerOutcome::retry()` | `release` | доставка возвращается брокеру для повторной доставки |
| `HandlerOutcome::drop()` | `reject` | окончательный исход; дальше решает политика недоставленных сообщений брокера |

На подписке at-most-once доставки приходят уже урегулированными, поэтому `ack` и `nack` возвращают
`AckError::Unsupported`.

В AMQP 1.0 нет отложенной повторной доставки, поэтому `HandlerOutcome::retry_after(delay)`
обслуживает отложенная перепубликация рантайма. Этому пути нужен собственный издатель, привязанный к
области через `retry_via`; без него задержка отбрасывается, и доставка сразу возвращается брокеру.

Копия уходит на собственный адрес подписки. Один узел AMQP - это и то, к чему присоединяется
получатель, и то, куда публикует отправитель, поэтому подписка здесь всегда может назвать адрес, по
которому издатель снова до неё дойдёт, а `retry_via` работает с любой подпиской этого брокера - и с
формой-дескриптором, и с простой формой `#[subscriber("orders")]`. В копии есть заголовок
`x-ruststream-retry-count` со счётчиком повторов, поэтому обработчик отличает первую доставку от
отложенной. На адресе `queue` она конкурирует за потребителей как любое другое сообщение, на адресе
`topic` её видит каждый подписчик.

## Публикация {#publishing}

`AmqpPublish` - политика, которая конструирует издателя `AmqpPublisher`. Политику вы указываете при
регистрации обработчика, а на старте она инстанцирует издателя на подключённом брокере. Она же -
политика по умолчанию этого брокера, поэтому обработчик `#[subscriber(.., publish)]` отвечает через
неё, если в точке монтирования издатель для ответа не назван.

Для ответа пишется `.out(Reply, Publish)`, для внедряемого слота -
`.out(<marker>, Publish).build()`; `Publish` - имя этой политики в [прелюдии](#the-prelude).
Настроек у политики нет, поэтому она пишется без аргументов.

Своих настроек нет и у отдельной публикации. Некоторые брокеры позволяют месту вызова настроить одно
сообщение - приоритет, срок жизни - шагом билдера публикации. Здесь такого шага нет, потому что этот
брокер не отправляет секцию `header` протокола AMQP, а `durable`, `priority` и `ttl` хранятся именно
в ней. Поэтому тело обработчика оставляет `Out<impl Publisher>` и ничего не импортирует из этого
крейта.

Отправляющая связь присоединяется при первой публикации и хранится по одной на адрес. Публикация,
которую брокер урегулировал не через `accept` (rejected, released, modified), возвращает ошибку,
поэтому отказ на стороне брокера не будет принят за успешную публикацию.

## Запрос и ответ {#requestreply}

Запрос и ответ есть в самом протоколе, поэтому `AmqpPublisher` реализует совместимость
`RequestReply`. `request(msg, timeout)` присоединяет динамическую принимающую связь, и брокер
выдаёт отдельный адрес для ответа на один этот запрос. Метод отправляет сообщение с заполненными
`reply-to` и `correlation-id` и завершается первым ответом, у которого совпал идентификатор
корреляции. Запрос, на который за отведённое время не ответили, возвращает ошибку; связь для ответа
отсоединяется в обоих случаях.

Запрос, который начинает обмен, не отвечает ни на какую доставку, поэтому он выполняется из хука
области `after_startup`, где издатель уже работает:

```rust
--8<-- "crates/ruststream-amqp/examples/amqp_request_reply.rs:request"
```

Отвечающая сторона читает адрес для ответа, названный запрашивающей, публикует ответ туда и
возвращает обратно `correlation-id`. Этот адрес новый для каждого запроса, поэтому ответ уходит
через внедрённого издателя, а не через возвращаемый из обработчика ответ, адресат которого задан ещё
при написании сервиса. Слот называет совместимость, нужную телу (`Out<impl Publisher>`), а
`b.include(greet).out(DefaultSlot, Publish).build()` привязывает политику к безымянному слоту,
который объявляет этот обработчик.

У типа приветствия нет `#[outgoing(name = ..)]`, поэтому адресата даёт место вызова: здесь это
переданный в `to(..)` адрес для ответа на конкретный запрос.

```rust
--8<-- "crates/ruststream-amqp/examples/amqp_request_reply.rs:responder"
```

Обе стороны собраны в
[`examples/amqp_request_reply.rs`](https://github.com/powersemmi/ruststream-amqp/blob/main/crates/ruststream-amqp/examples/amqp_request_reply.rs).

## Транзакции {#transactions}

С фичей `transaction` политика `AmqpTransactionalPublish` конструирует транзакционного издателя
`AmqpTxnPublisher`, а тот публикует через транзакционную отправку протокола. `begin_transaction`,
`commit` и `abort` есть только у этого издателя, поэтому вы получаете их, указав эту политику вместо
`Publish`.

```rust
--8<-- "crates/ruststream-amqp/examples/amqp_transaction.rs:transaction"
```

Дескриптор держит не больше одной транзакции на стороне брокера. Второй `begin_transaction` при
открытой транзакции возвращает ошибку и оставляет открытую транзакцию нетронутой, а `commit` или
`abort` без открытой транзакции тоже возвращают ошибку. Фиксация или откат, вернувшие ошибку, всё
равно закрывают транзакцию, поэтому следующий `begin_transaction` открывает новую. Публикация вне
транзакции уходит сразу, через того же издателя.

Транзакция охватывает публикацию: приём и урегулирование доставок в неё не входят.

## Заголовки и ключ партиционирования {#headers-and-the-partition-key}

Стандартные заголовки отображаются на секцию `properties` протокола AMQP: `content-type`,
`correlation-id`, `reply-to`, `message-id` и ключ партиционирования как `group-id`. Остальные
заголовки попадают в `application-properties`. Собственного конверта у фреймворка нет, поэтому
сторона на другом стеке видит обычное сообщение AMQP, а сообщение от другого клиента AMQP приходит с
сохранёнными заголовками.

Ключ партиционирования - это заголовок `partition-key` (экспортирован как `PARTITION_KEY_HEADER`), а
доставленное сообщение реализует совместимость `Partitioned`.

## Тестирование {#testing}

Фича `testing` даёт `AmqpTestBroker` - транспорт внутри процесса, который воспроизводит поведение
этого крейта без сервера и без передачи по AMQP. Тестовый файл импортирует его отдельным путём,
`use ruststream_amqp::testing::AmqpTestBroker;`, рядом с glob прелюдии. Он проходит ту же
последовательность переходов, что и настоящий брокер, и работает с обвязкой `TestApp`. См.
[Юнит-тестирование сервиса через TestApp](https://powersemmi.github.io/ruststream/latest/guides/testing/#unit-testing-a-service-with-testapp).

Против тестового брокера разрешается вся боевая декларация целиком, поэтому тест выполняет то
связывание, которое поставляет сервис, а не переписанную его копию.
`#[subscriber(AmqpAddress::queue("orders"))]`
монтируется на `AmqpTestBroker` без изменений, `.out(Reply, Publish)` монтирует боевую политику, а
`AmqpTransactionalPublish` конструирует внутрипроцессного издателя, который буферизует публикации до
фиксации. Нет ни отдельной тестовой политики, которую подменяют в точке монтирования, ни
совместимости, которая есть на одном брокере и отсутствует на другом: `RequestReply` и
`TransactionalPublisher` перенесены, поэтому обработчик со слотом `Out<impl RequestReply>` или
`Out<impl TransactionalPublisher>` монтируется и внутри процесса.

Вместе с ними перенесено и поведение, потому что тест, который не может провалиться, ничего не
стоит. Доставку здесь решает терминус, как и на сервере: подписки `AmqpAddress::queue` на одном
адресе конкурируют за каждое сообщение, а подписки `AmqpAddress::topic` получают по копии, поэтому
сервис с очередью заданий не пройдёт внутри процесса то, что провалил бы настоящий брокер. Адрес
`AmqpAddress::raw` не объявляет возможности, поэтому сервер смотрит в собственную конфигурацию, а у
внутрипроцессного брокера конфигурации нет, и он доставляет каждое сообщение один раз; там, где
проверяется именно доставка всем подписчикам разом, указывайте `topic`. Доставка at-most-once
приходит урегулированной,
и её `ack` возвращает `AckError::Unsupported`. Пакеты собирает тот же клиентский буфер, с
`batch_wait` из дескриптора. Транзакция ничего не публикует до фиксации и отбрасывает свой буфер при
откате, а нарушение порядка вызовов (второй `begin_transaction`, фиксация без открытой транзакции)
возвращает ошибку, а не проходит молча. В запросе заполнены `reply-to` и `correlation-id`, он
завершается ответом с совпавшей корреляцией и возвращает `AmqpError::RequestTimeout`, когда никто не
ответил.

Не воспроизведено то, что хранит брокер и не может хранить процесс; каждый такой пункт делает
проверку не просто неточной, а неверной:

- **Нет хранения.** Сообщение, опубликованное на адрес без живой подписки, записывается в журнал и
  отбрасывается, тогда как сервер придержал бы его для потребителя, который присоединится позже.
  Открывайте подписки первыми.
- **Нет повторной доставки на стороне брокера.** Освобождённая доставка возвращается той подписке,
  у которой была, и никогда не конкурирующему потребителю, а за `nack(requeue = false)` нет политики
  недоставленных сообщений.
- **Нет долговечности.** Зафиксированная транзакция атомарна настолько, насколько это видит
  обработчик, но буфер лежит в этом процессе: ничто не переживает аварийного завершения, а тайм-аута
  транзакции и ограждения на стороне брокера нет.
- **Нет управления потоком.** У `credit` здесь нет соответствия. Придерживать сообщения так, как это
  делает связь, значило бы превратить роутер в очередь на стороне брокера, и ни один обработчик не
  заметил бы разницы, поэтому внутрипроцессные подписки не ограничены, а окно предвыборки здесь не
  проверить.
